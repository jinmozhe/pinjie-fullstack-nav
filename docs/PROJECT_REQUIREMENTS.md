# Pinjie Fullstack Nav 产品需求基线

> 文档状态：生效，导航管理与管理员只读查阅需求已确认
> 适用范围：`pinjie-fullstack-nav`
> 最后更新：2026-09-07

## 1. 文档定位

本文件是 `pinjie-fullstack-nav` 的产品需求权威来源，定义项目身份、继承基线、当前确认需求、非目标、独立演进规则和验收边界。

本文件描述“Nav 项目需要具备什么”，不把目标需求表述为已经实现。相关事实按以下来源维护：

| 信息 | 权威来源 |
| --- | --- |
| 项目身份、当前阶段、活动计划和权威入口 | `PROJECT_INDEX.md` |
| 详细实现状态 | 实际源码、配置、迁移、生成契约和对应架构文档 |
| 全部实施计划永久登记 | `plans/INDEX.md` |
| 已交付能力和版本变化 | `CHANGELOG.md` |
| 技术选型及其理由 | `docs/adr/` |
| 工程结构和实现边界 | `docs/architecture/` 和各级 `AGENTS.md` |
| 具体实施方案和验证结果 | `plans/*.md` |
| Nav 业务详细需求 | 本文件中的 `NAV-*` 需求和对应 `plans/*.md` |
| 继承的业务扩展参考 | `docs/blueprints/`，采用前必须进入当前 PRD 和计划 |

PRD 与当前实现不一致时，以本文件判断目标范围，以实际源码、配置、迁移、生成契约和对应架构文档判断详细实现状态，并通过新的全栈计划处理差距。`PROJECT_INDEX.md` 只负责项目身份、当前阶段、活动计划和权威入口，不得仅修改根索引或 Changelog 来改变产品需求或伪造实现状态。

本文件中的 `BASE-*` 需求保留为从母版继承的技术与治理基线；`NAV-*` 需求描述当前项目自身范围。母版措辞只说明上游能力来源，不代表本仓库继续承担通用母版职责。

## 2. 产品背景

`pinjie-fullstack-nav` 用于开发独立导航站业务。项目从 `pinjie-fullstack-base` 继承可运行的 Backend、Admin、Web、API Client、数据库迁移、质量门禁和部署基础，减少重复搭建工作。

当前派生事实如下：

1. 母版发布基线为 `v1.0.0`，对应 Commit `7f5f4ad28b73ffabe3c0fa9cc99b39875482ba18`。
2. 实际拉取的母版源码快照为 `00b409ae866b260854b75bef74c16cd4b9692c79`，即 `v1.0.0-1-g00b409a`；该提交增加派生项目计划基线规则。
3. 当前仓库是独立 Git 仓库，远程只指向 `jinmozhe/pinjie-fullstack-nav`，运行时不依赖母版本机目录。
4. 母版继承计划已由用户在派生初始化阶段人工清理，后续 Nav 计划单独永久登记。
5. 当前目标是个人使用的公开导航与外网凭据资料库：后台统一维护，管理员在 Web 只读查阅；审核、推荐和商业化不属于首版范围。

## 3. 目标用户

| 用户 | 主要需求 |
| --- | --- |
| 项目负责人 | 确认导航站产品范围、优先级、验收标准和发布边界 |
| 产品与运营负责人 | 在后续计划中定义内容组织、收录和运营流程等具体需求 |
| Backend 开发者 | 在统一分层、事务、迁移和安全边界内扩展领域能力 |
| Admin 开发者 | 基于统一契约和管理端组件体系实现运营与管理流程 |
| Web 开发者 | 基于统一契约、SSR 和设计体系实现用户端体验 |
| 项目协作者和 AI | 通过索引、PRD、计划和文档快速确认目标、现状与执行范围 |

导航访客可以公开浏览；具备凭据查看权限的管理员可以登录 Web 查阅全部外网帐号、密码和备注。导航业务不关联普通用户，既有普通用户与注册功能保留。

## 4. 核心使用场景

1. 基于继承的全栈基础确认导航站目标用户、内容边界、核心流程和验收标准。
2. 通过同一份全栈计划扩展 Backend 领域、Admin 运营能力、Web 用户体验和共享 API 契约。
3. 继续使用继承的认证、用户、权限、资产、系统设置、质量门禁和部署能力。
4. 在独立仓库中发布、部署和运维 Nav 项目，不依赖母版工作区或母版远程。
5. 需要吸收母版后续变化时，以不可变 Tag、完整 Commit SHA 和明确差异为依据建立专项计划。

## 5. 适用与不适用范围

### 5.1 当前适用

- 采用 FastAPI、PostgreSQL、Admin 和 Web 的独立导航站全栈项目。
- 需要认证、用户、权限、资产、系统设置、契约生成和部署基础的后续业务开发。
- 需要通过 PRD、全栈计划、ADR、文档索引和 Changelog 长期维护项目事实。

### 5.2 当前不适用

- 把项目名称直接当作导航分类、收录、搜索、审核、推荐或商业化功能已经确认的依据。
- 把继承的蓝图、母版历史计划或母版 Changelog 当作 Nav 业务已经实施的证据。
- 让当前仓库自动跟踪母版更新，或建立指向母版本机目录的运行时依赖。

### 5.3 当前确认需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| NAV-GEN-001 | 项目必须作为独立导航站全栈仓库演进 | 项目身份、远程、业务范围和交付记录均属于 `pinjie-fullstack-nav`，运行时不依赖母版目录 |
| NAV-GEN-002 | 项目必须准确追溯继承来源 | `PROJECT_INDEX.md` 同时记录母版发布 Tag、对应完整 Commit SHA 和实际派生源码快照 |
| NAV-DOC-001 | 项目必须建立独立计划基线 | `plans/` 只登记当前项目实际存在的计划；一次性清理结束后，所有新增计划永久保留 |
| NAV-DOC-002 | 详细导航业务必须先确认需求再实施 | 首个业务计划补充目标用户、核心场景、功能范围、非目标和验收标准，并新增对应 `NAV-*` 需求 |
| NAV-QUAL-001 | 继承的安全、质量和契约边界不得静默削弱 | 调整适用的 `BASE-*` 需求必须通过 ADR、全栈计划和用户确认记录原因及验证 |
| NAV-CAT-001 | 导航采用一级分类 | 每个站点必须且只能属于一个分类；分类支持名称、说明、排序、启停和可选内置图标；图标可搜索选择、预览及清除，未选择显示默认图标，Admin 与 Web 按同一标识展示相应语义；有站点引用时禁止删除 |
| NAV-CAT-002 | 分类可配置仅管理员查阅登录后可见 | 默认公开；访客和普通用户登录均不可读取受限分类及其站点；有效管理员查阅会话可见；分类停用始终隐藏；搜索、标签筛选和分页计数统一过滤；退出和身份失效时清理受限内容及缓存 |
| NAV-TAG-001 | 站点可以关联多个标签 | 标签名称唯一，站点标签组合唯一；删除标签只解除关联，不删除站点 |
| NAV-SITE-001 | 后台统一维护站点生命周期 | 支持名称、网址、简介、图标、分类、标签、排序、发布、下架、回收站及恢复；回收站支持独立权限控制、二次确认后的单条及批量永久删除，同一事务删除站点、所属帐号资料和标签关联，保留分类、标签、图标资产与审计，正常站点禁止直接永久删除；公开查询只显示未删除且已发布、分类启用的站点 |
| NAV-CRED-001 | 每站点可以保存多条外网帐号或备注 | 不关联普通用户；名称、用户名、明文密码、备注、排序、启用状态分别保存；用户名、密码、备注至少填写一项；密码原样保存，授权后明文展示，帐号支持物理删除 |
| NAV-AUTH-001 | Web 使用管理员身份只读查阅 | 复用现有管理员登录入口，已有后台登录可免重复输入；签发独立只读会话，普通用户和访客不可读取凭据，Web 查阅会话不可用于管理写接口 |
| NAV-AUTH-002 | 两端独立退出 | Web 只退出当前查阅会话，Admin 退出保持原逻辑；Web 主动退出后不自动重新登录，显式登录才能恢复；不新增退出全部登录功能 |
| NAV-WEB-001 | Web 提供公开导航与授权凭据查阅 | 公开搜索、分类和标签筛选、访问站点；登录后查看及复制对应帐号、明文密码、备注；不提供业务新增、修改、删除入口 |
| NAV-ADMIN-001 | 所有导航维护均在管理端完成 | 沿用现有组件、权限与审计；管理分类、标签、站点和帐号，列表具有合法批量操作；凭据不进入日志、审计、公开响应和共享缓存 |

## 6. 继承的母版产品原则

以下 `BASE-*` 需求保留其上游编号，作为当前项目的继承技术基线。具体适用性由本文件、实际实现和后续 Nav 计划共同判断。

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-GEN-001 | 母版必须以一个全栈 Monorepo 管理 Backend、Admin、Web 和共享包 | 三个应用边界清楚，共享只通过 `packages/` 的公开包发生 |
| BASE-GEN-002 | 母版必须只包含跨业务可复用能力 | 具体 CMS、电商、博客业务只存在于蓝图或派生仓库 |
| BASE-GEN-003 | 母版必须支持独立派生和运行 | 派生仓库运行时不依赖母版本机目录或其他参考项目绝对路径 |
| BASE-GEN-004 | 目标能力、阶段导航、详细实现、实施过程和交付历史必须分开维护 | PRD、根项目索引、实际文件与架构文档、计划和 Changelog 各自拥有明确职责 |
| BASE-GEN-005 | 跨栈功能必须作为一项完整能力规划和验收 | 同一功能使用一份全栈计划覆盖涉及的应用、契约、数据和部署范围 |
| BASE-GEN-006 | 母版及派生项目必须能够追溯基线 | 派生项目同时记录母版不可变 Tag、完整 40 位 Commit SHA、派生类型、阶段和业务范围 |
| BASE-GEN-007 | 母版必须采用可机械验证的模块化边界 | 应用、领域和 Feature 只通过公开入口协作，越层、跨域内部引用和循环依赖由自动门禁拒绝 |
| BASE-GEN-008 | 临时兼容只能用于受控迁移 | 兼容窗口具备范围、负责人、删除日期、观测指标、回滚条件和删除测试，禁止永久或隐式兼容 |

## 7. Backend 目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-BE-001 | 提供可配置、可启动和可健康检查的 FastAPI 应用 | 本地环境可以启动应用，健康检查不依赖具体业务数据 |
| BASE-BE-002 | 提供统一的成功响应、业务异常和请求追踪机制 | 公开 API 使用统一响应契约，顶层 `message` 使用中文，错误包含可定位的请求标识且不泄露敏感信息 |
| BASE-BE-003 | 提供认证与会话基础能力 | 支持派生项目实现登录、可关闭的公开注册、身份校验、当前用户读取和登录失效处理；用户与管理员新密码统一为 6 至 64 个字符，不使用默认生产密钥 |
| BASE-BE-004 | 提供用户账户基础能力 | 支持 Admin 独立创建用户、用户资料（含受控头像绑定）、账户状态、统一软删除与长期可恢复回收站；恢复后保持停用，具体业务画像由派生项目扩展 |
| BASE-BE-005 | 提供管理身份和 RBAC 基础 | 支持管理员身份、角色、权限和受保护管理接口，复杂 ABAC 或组织模型不进入母版默认范围 |
| BASE-BE-006 | 提供系统级公共能力入口 | 健康、配置、审计、限流和缓存等能力通过公共基础设施或 system 领域统一承载 |
| BASE-BE-007 | 数据访问必须具有明确分层和事务边界 | Router、Service、Repository、Model 和 Schema 职责可由规则与测试验证，事务由 Service 控制 |
| BASE-BE-008 | 外部输入和外部系统调用必须安全失败 | 输入在边界校验，外部请求具有超时、有限重试和幂等边界，不静默吞错 |
| BASE-BE-009 | 每个领域必须拥有自己的写模型和内部实现 | 跨领域写流程只通过公开 Application Service、Port、DTO 或领域事件编排，其他领域不得直接访问 Repository、Model 或内部 Service |
| BASE-BE-010 | Admin 管理端点必须声明资源权限 | 每个新增管理端点在 Router 显式声明准确 `PermissionCode`；缺少目录项时先更新源码权限目录并通过受控同步写入目标环境，禁止只校验管理员登录态 |
| BASE-BE-011 | 提供强类型运行时系统设置 | 站点资料与公开注册使用数据库权威配置、固定 Schema、revision 并发保护和审计；注册配置失败时保持关闭，配置媒体与文件资产隔离 |

## 8. Admin 目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-ADMIN-001 | 提供可扩展的 B 端管理应用骨架 | 应用具有路由、布局、导航、认证入口和统一错误处理能力 |
| BASE-ADMIN-002 | 提供管理员登录与权限入口 | 未认证和无权限状态可识别，受保护页面不能仅依赖界面隐藏控制访问 |
| BASE-ADMIN-003 | 提供用户、管理员、角色、权限和系统管理的扩展位置 | 用户管理包含受独立权限控制的创建、正常列表、回收站和单条及批量恢复；通用管理能力边界清楚，具体业务运营页面由派生项目增加 |
| BASE-ADMIN-004 | 管理界面必须覆盖完整操作状态 | 表格、表单和操作流程覆盖加载、空数据、失败、无权限和成功；软删除、硬删除及已保存图片移除等持久化删除的单条和批量入口均使用统一标准警告弹窗，取消不写入、提交防重复、失败保留目标；依据 ADR 0017 修订确认范围 |
| BASE-ADMIN-005 | 管理端必须适合高频工作操作 | 界面紧凑、可扫描，支持筛选、比较、重复操作、长文本和窄屏溢出处理 |
| BASE-ADMIN-006 | 页面只通过共享 API Client 消费后端契约 | 不在页面复制 OpenAPI DTO，不绕过统一 HTTP、认证和错误处理入口 |
| BASE-ADMIN-007 | 数据列表必须提供与生命周期一致的批量操作 | 除登录安全事件、审计事件、请求元数据及产品明确登记的不可变历史记录外，列表按权限提供批量选择和至少一种有效批量操作；软删除实体批量软删除，硬删除实体批量硬删除，未定义删除生命周期的实体提供状态等合法批量操作 |
| BASE-ADMIN-008 | 提供固定、强类型的系统设置界面 | 站点资料与公开注册使用对应 Ant Design 组件，按精确读写权限显示只读或编辑状态，revision 冲突保留草稿并要求明确刷新 |

## 9. Web 目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-WEB-001 | 提供可扩展的 C 端 Next.js 应用骨架 | 应用具有布局、路由、错误边界、加载状态和领域扩展位置 |
| BASE-WEB-002 | 提供认证和用户中心基础能力 | 派生项目能够接入登录、服从 Backend 权威开关的公开注册入口、退出、当前用户资料（含头像上传、更换、移除和失效回退）和受保护用户页面 |
| BASE-WEB-003 | 需要收录的页面必须具备服务端首屏和准确 Metadata | 页面提供语义化标题、canonical 及必要结构化数据，首屏不依赖纯客户端空壳 |
| BASE-WEB-004 | 用户端必须具备稳定的响应式和可访问性基线 | 桌面和移动端无横向溢出与遮挡，键盘、焦点、标签和对比度可验证 |
| BASE-WEB-005 | UI 扩展必须遵守统一组件和设计 token 边界 | 定制 UI 先维护 tokens 和基础组件，避免页面散落不受控视觉值 |
| BASE-WEB-006 | 页面只通过共享 API Client 或明确的服务端请求入口消费后端 | 不复制 OpenAPI DTO，公开地址与仅服务端地址边界清楚 |
| BASE-WEB-007 | 母版不预设具体业务首页 | 派生项目根据目标用户设计首屏，母版只提供可复用布局和基础体验 |
| BASE-WEB-008 | 用户侧品牌必须消费公开站点资料 | 首页、认证和用户中心通过服务端 SiteProfile 使用站点名称、LOGO 与 Metadata；展示读取失败时使用内置回退且不影响注册安全判断 |

## 10. API 与共享包目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-API-001 | 根 `openapi.json` 必须是唯一 OpenAPI 契约 | 契约由 Backend 导出，面向开发者的标题、分组、接口摘要、字段说明和响应说明使用中文，路径、参数、字段与程序标识保留英文；禁止手工编辑和维护应用内副本 |
| BASE-API-002 | `packages/api-client/src/` 必须由根契约生成 | 生成过程可重复，Admin 和 Web 使用同一份类型和请求能力 |
| BASE-API-003 | 契约变化必须按固定顺序同步 | Backend 实现、OpenAPI 导出、API Client 生成、前端适配和跨栈验证在同一计划内完成 |
| BASE-API-004 | 共享包必须保持业务中立 | 只承载明确跨应用复用的客户端、Lint 和 TypeScript 配置，不承载单一派生项目业务实现 |
| BASE-API-005 | 公开契约变更必须识别并审查破坏性影响 | 移除字段、改变类型或语义、改变方法或路径、收紧约束及改变错误契约必须在同一全栈计划中完成消费者迁移或明确的受控兼容窗口 |

## 11. Database 目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-DB-001 | PostgreSQL 必须作为关系数据权威来源 | 本地、测试和生产数据库明确隔离，不使用内存数据库替代关键行为验证 |
| BASE-DB-002 | 数据库结构必须通过 Alembic 演进 | Model 变化具有对应迁移，能够验证空库升级和重复升级 |
| BASE-DB-003 | 异步数据访问必须避免隐式查询和失控事务 | 关联加载、事务提交和查询边界符合 Backend 规则并有测试覆盖 |
| BASE-DB-004 | 派生业务的数据不变量必须由派生项目定义 | 母版不预设商品、内容、订单等业务表和约束 |
| BASE-DB-005 | 数据结构变化必须保护数据所有权和可恢复性 | 迁移包含升级验证、数据校验和失败恢复边界；不可逆变更必须具备已验证备份和专项确认 |

## 12. 本地开发、质量与部署目标需求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| BASE-OPS-001 | 提供 Windows 可复现的本地开发流程 | 使用 uv、pnpm、本机 PostgreSQL 和 Docker Desktop Redis，步骤由运维文档覆盖 |
| BASE-OPS-002 | 依赖必须由唯一锁文件管理 | 根目录只维护一份 `pnpm-lock.yaml`，Backend 只维护 `apps/backend/uv.lock` |
| BASE-OPS-003 | 每个应用必须具备可执行的质量能力和轻量自动门禁 | Backend 自动执行静态、类型、导入和契约检查，Admin 与 Web 自动执行 Lint 和类型检查；构建与测试能力继续保留，只在用户明确授权后运行 |
| BASE-OPS-004 | 跨栈契约变化必须保持机器契约一致 | OpenAPI 导出、API Client 生成、Breaking Change 和受影响前端类型检查进入同一计划；构建与测试结果仅在明确授权后补充 |
| BASE-OPS-005 | 应用必须具备容器化生产交付路径 | Backend、Admin 和 Web 可构建独立镜像，生产配置不打包真实密钥 |
| BASE-OPS-006 | 部署流程必须支持安全升级和失败恢复 | 数据迁移、镜像版本、健康检查、回滚和备份边界有可执行文档 |
| BASE-OPS-007 | CI 和发布必须分离 | Push 与 Pull Request 只执行轻量静态、契约、治理和安全检查；镜像发布与部署分别授权，发布所需制品构建不代表测试通过 |
| BASE-OPS-008 | CI 必须以 Fail Closed 方式处理已配置的自动门禁 | 空骨架、部分实现和完整应用状态可区分；轻量静态门禁、生成漂移、契约破坏和安全检查失败时必须停止，未获授权的构建与测试如实记录为未执行 |
| BASE-OPS-009 | 发布物和生产部署必须不可变且可验证 | 构建绑定完整 Commit SHA，镜像提供 SBOM 和构建来源证明，生产部署固定镜像 digest，禁止使用 `latest` 或缺失版本回退 |
| BASE-OPS-010 | 母版必须区分单机可恢复和多实例高可用部署 | 当前部署等级、适用边界、健康检查、回滚、备份恢复及故障转移要求有明确文档，单机部署不得宣称高可用 |
| BASE-OPS-011 | 派生项目必须按业务风险定义可靠性目标 | 生产前明确关键用户链路的 SLI、SLO、错误预算、RTO 和 RPO，并通过容量测试和恢复演练验证 |

## 13. 安全与质量要求

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |

| BASE-SEC-005 | 软件开发和供应链必须采用分层安全门禁 | 仓库定义漏洞报告、代码所有权和高风险评审；秘密、代码、依赖、容器和构建来源在对应阶段接受可重复检查 |
| BASE-SEC-006 | 认证、授权和高风险操作必须可审计 | 权限默认拒绝，资源授权在服务端结合资源状态执行，审计记录可关联请求和发布版本且不保存凭据或完整敏感载荷 |

| BASE-QUAL-002 | 已有功能、配置和 UI 行为必须在修改中得到保护 | 未经明确授权不得精简、替换或弱化既有能力 |
| BASE-QUAL-003 | 文本和配置资产必须具有稳定格式 | 源码、配置和文档使用 UTF-8 无 BOM并保留末尾换行 |
| BASE-QUAL-004 | 失败和故障隔离必须具有显式契约 | 禁止吞错、假成功、弱默认值和静默降级；允许的超时、有限重试、熔断、背压和只读状态必须可观测并具有恢复条件 |

## 15. Nav 项目明确非目标

当前阶段不承担以下目标：

1. 继续作为 CMS、电商、博客或其他业务的通用派生母版维护。
2. 自动同步母版的新提交、Tag、分支、计划或发布记录。
3. 首版不提供审核、推荐、商业化、外网自动登录、抓取、帐号有效性探测、子分类或按普通用户隔离的私人帐号。
4. 默认引入商品、库存、订单、支付等与导航站需求无关的业务领域。
5. 在仓库中保存生产数据、默认管理员凭据、真实域名、证书和平台密钥。
6. 为兼容任意框架而维护 Django、Nuxt、Vue、Java 或 .NET 的平行实现。

后续确认的新业务能力必须先更新 `NAV-*` 需求并通过全栈计划实施，不能从项目名称、继承蓝图或母版历史中自动推导。

## 16. 继承与独立演进规则

1. 本项目是独立仓库，不建立指向母版绝对路径的运行时依赖，也不保留母版 Git 远程。
2. 母版发布基线为 `v1.0.0`，对应 Commit `7f5f4ad28b73ffabe3c0fa9cc99b39875482ba18`。
3. 实际派生源码快照为 `00b409ae866b260854b75bef74c16cd4b9692c79`；该快照比 `v1.0.0` 多一个派生计划治理提交，必须与发布 Tag 分开记录。
4. 后续吸收母版变化时，必须建立专项计划，核对准确提交范围、当前项目修改、契约、迁移、验证和回滚边界。
5. 适用的 `BASE-*` 安全、质量、架构和契约要求继续生效；调整或取消时必须通过 ADR、全栈计划和用户确认记录。
6. 用户已在派生初始化阶段人工一次性删除母版继承计划，`plans/INDEX.md` 按当前文件事实重建，不保留失效登记。
7. 一次性清理窗口已经结束。本项目现存及后续新增计划永久保留，AI 不得删除、移动、重命名或替换。
8. 通用且经过 Nav 项目验证的能力是否回馈母版，需要独立评估和授权，不影响当前仓库独立演进。

## 17. 当前阶段验收

派生初始化达到可开始产品需求设计的条件时，必须同时满足：

1. `PROJECT_INDEX.md` 准确记录项目名称、角色、派生类型、当前阶段和业务范围。
2. 母版发布 Tag、对应完整 Commit SHA 和实际派生源码快照分别记录，不混淆版本含义。
3. Git 远程只指向 `jinmozhe/pinjie-fullstack-nav`，不保留母版远程或运行时目录依赖。
4. `plans/` 只保留当前项目实际存在的计划，`plans/INDEX.md` 不包含已清理计划的失效登记。
5. `plans/README.md` 明确一次性初始化例外已经结束，后续计划恢复永久保护。
6. 本 PRD 区分 `NAV-*` 当前项目需求、`BASE-*` 继承基线和尚未确认的导航业务细则。
7. 根 README、项目规则、项目索引和文档索引使用当前项目身份。
8. 首个导航业务实现开始前，用户确认详细目标用户、核心场景、功能范围、非目标和验收标准。

当前是否满足具体业务能力的验收条件，必须综合实际源码、配置、迁移、生成契约、对应架构文档、计划验证结果和 `CHANGELOG.md` 判断。项目索引和计划索引只承担导航与登记职责，不能单独证明功能已经实现。

## 18. 需求追踪规则

1. 新计划必须包含“关联需求”，优先引用一个或多个 `NAV-*` 编号；涉及继承技术基线时同时引用适用的 `BASE-*` 编号。
2. 首个业务计划必须补充导航站详细目标用户、核心场景、功能范围、非目标、验收标准和对应 `NAV-*` 编号。
3. 新增、修改或取消产品能力时，必须先更新本 PRD，或在同一计划中列明 PRD 变更并取得用户确认。
4. 技术实现变化但产品需求不变时，只更新计划、架构文档或 ADR，不机械修改 PRD。
5. 需求完成后，在计划中记录验证证据，并在 `CHANGELOG.md` 记录已交付能力。
6. 根项目索引只记录项目身份、当前阶段、活动计划和权威入口，不复制需求正文或详细实现状态。

## 19. 术语

| 术语 | 含义 |
| --- | --- |
| 母版 | 提供本项目初始通用全栈能力的独立上游仓库 `pinjie-fullstack-base` |
| 母版发布基线 | 不可变 Tag `v1.0.0` 及其对应 Commit `7f5f4ad28b73ffabe3c0fa9cc99b39875482ba18` |
| 派生源码快照 | 本项目实际拉取的母版 Commit `00b409ae866b260854b75bef74c16cd4b9692c79` |
| `BASE-*` 需求 | 从母版继承的技术、质量、安全、契约和治理基线 |
| `NAV-*` 需求 | `pinjie-fullstack-nav` 自身的产品与项目需求 |
| 目标能力 | 本 PRD 规定项目最终需要达到的能力，不代表当前已完成 |
| 当前阶段 | 当前仓库所处的高层阶段和活动工作摘要，由 `PROJECT_INDEX.md` 维护 |
| 详细实现状态 | 当前仓库已经存在的具体能力和运行机制，以实际源码、配置、迁移、生成契约和对应架构文档为证据 |
| 全栈计划 | 面向整个 Monorepo，统一评估 Backend、Admin、Web 和跨栈范围的实施计划 |
| 权威来源 | 某类信息唯一允许维护完整事实的文件或生成链路 |
| Fail Closed | 前置条件、验证或依赖不满足时明确失败并阻止继续，不返回假成功或自动选择弱化路径 |
| 受控迁移窗口 | 为滚动升级临时保留的新旧契约重叠期，具有明确范围、期限、观测、回滚和删除条件 |
| 不可变发布物 | 内容由完整 Commit SHA 和镜像 digest 唯一确定，已发布内容不能在保持同一标识时被替换 |
| 单机可恢复模式 | 允许短时中断，通过不可变版本、备份、恢复验证和回滚控制风险的部署等级，不等同于高可用 |
