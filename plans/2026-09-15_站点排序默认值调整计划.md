# 站点排序默认值调整计划

## 1. 当前状态和结果

- 状态：已结束
- 结果：已完成；站点查询排序、默认值、OpenAPI 同步和轻量门禁完成，Backend 编译与应用导入受既有语法错误阻断，重型验证未执行

## 2. 关联需求

- `NAV-SITE-001`：后台维护站点排序。
- `NAV-WEB-009`：Web 置顶页沿用站点排序。

## 3. 背景

当前站点查询按 `sort_order` 升序、站点 ID 升序排列，新建站点默认 `sort_order=0`。这会使人工填写的正数排序值排在默认站点之后，也会让同排序值的站点按较早生成的 UUID v7 在前。

## 4. 目标

- 所有站点列表和首页分组预览统一按 `sort_order` 升序、`id` 倒序排列。
- 新建站点默认使用当前允许范围的最大排序值 `1_000_000`，让合法人工排序值默认优先。
- 保持现有站点数据不变，不覆盖历史上明确填写的 `0`。

## 5. 非目标

- 不执行数据库数据迁移。
- 不改变分类、标签、帐号和置顶字段的排序语义。
- 不改变 API 路径、响应结构和分页参数。

## 6. 现状分析

- `NavigationRepository.sites` 和 `groups` 负责站点排序。
- Admin 和 Web 端均直接消费后端顺序，没有独立的站点排序器。
- `NavSiteIn`、`NavSite` 和 Admin 新建表单各自维护默认排序值。

## 7. 方案设计

- 查询使用 `sort_order ASC, id DESC`，窗口函数和最终分组查询保持同一排序键。
- 将新站点默认值在后端输入 Schema、ORM 模型和 Admin 新建表单统一调整为 `1_000_000`。
- 在导航架构文档中明确排序方向、默认值和历史数据处理边界。

## 11. 风险与回滚

- 风险：历史 `sort_order=0` 无法从数据层区分默认值和用户明确填写值，因此本次不自动改写。
- 风险：同排序值改为 ID 倒序会改变同值站点的相对顺序。
- 回滚：恢复本计划列出的源码和文档差异即可，不涉及数据库结构或数据回滚。
