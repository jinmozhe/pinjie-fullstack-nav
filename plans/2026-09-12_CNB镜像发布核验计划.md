## 现状与方案

目标版本的 GitHub 四项 Push CI、Full Validation 和 strict 源码交接已成功。本机 CNB API 未登录，Docker 查询 TCR 返回 unauthorized，浏览器工具不支持当前认证方式。新增人工只读诊断工作流，在原 `cnb-source-handoff` Environment 内使用既有凭据查询固定 CNB 仓库，不复制凭据到本地、不修改权限、不触发构建。

按 CNB 官方 OpenAPI 查询目标 SHA 的构建列表和各阶段状态。输出仅包含构建标识、流水线与阶段状态，失败显式传播；诊断运行成功仅代表查询完成，不代表镜像发布成功。进一步依据实际失败阶段修复，镜像存在性须由 TCR digest 和发布证据确认。

## 规则落实与实施

- 根规则及开发流程第 17、18.1 节：精确暂存，通过 PR 交付，保留必需检查；只执行适用轻量门禁。
- ADR 0008：固定目标 SHA，保留 strict 验证、镜像扫描和不可变标签约束；查询失败不降低发布门禁。
- SECURITY：凭据仅在原受保护环境使用；固定请求目标、只读 GET、拒绝重定向，不输出原始响应或凭据。
- 影响文件：`.github/workflows/inspect-cnb-release.yml`、现有发布手册、`CHANGELOG.md`、本计划与两个索引。
- 顺序：登记计划，实现并检查只读入口，完成 Git 交付，查询 CNB，再根据证据处理发布链路。

## 风险与回滚

既有 Token 可能缺少 `repo-cnb-history:r` 或 `repo-cnb-trigger:r`。缺权时报告准确权限，不自行修改凭据或扩大授权。工作流无自动触发和远端写入；回滚通过普通 PR 撤销入口，不影响已存在镜像。
